# 工作紀錄：長錄音分段、TXT 合併與詞庫回吐防護

日期：2026-08-02  
專案：`record-to-text`  
基準 commit：`4179b8f`（已 push 至 `codex/record-to-text-hardening`）

## 一、這次到底要做什麼

這一輪不是單純加一個按鈕，而是把長錄音的實際工作流程補完整：

1. 外部程序要有 timeout／watchdog，避免 `ffprobe`、`ffmpeg`、OpenCC 或 ASR helper 卡死。
2. 轉錄前檢查暫存碟與輸出碟空間。
3. 最近工作能辨識來源檔或輸出檔已不存在，並保留合理的完成／失敗日誌。
4. 同一批工作重用 ASR helper 與模型 cache，減少每段都重新出現 `Fetching 11 files`。
5. 輸出在逐段、合併與 OpenCC 後重新驗證，不能只因程序結束就標示完成。
6. 錄音加入佇列後，可以在「開始轉文字」旁選擇「切分再依序轉」，把單一錄音切成前後兩段；第一段先處理，第二段排隊。
7. 多份分段 TXT 可以依段落編號排序合併成新檔，原始 TXT 不覆寫。

原先列出的 PD-015「自動檢查更新」沒有放進這一輪，仍是後續產品發佈流程的一項工作。

## 二、原本的規劃

### 1. 先把資料流拆清楚

原本的主流程是：

```text
音檔
  → ffprobe 取得長度
  → ffmpeg 產生暫存 WAV
  → ASR helper
  → OpenCC
  → 輸出 TXT
```

這次把它延伸成：

```text
來源音檔
  → 可選的前／後半段 source slice
  → coordinator segment
  → helper 內部 chunk
  → 每段輸出契約驗證
  → 依順序合併
  → OpenCC
  → final output contract
  → 原子寫入 TXT
```

關鍵原則是：只要其中一段失敗、空白或輸出看起來是 Prompt 回吐，就不能把正式 TXT 當成成功結果；必要時保留 recovery 草稿供診斷。

### 2. 再補 UI 與資料模型

- 佇列中的工作增加來源時間範圍與段落標籤。
- 切分後建立兩個有順序的工作，而不是把兩段內容混成一個不可追蹤的工作。
- 合併功能只讀取 TXT、依檔名中的段落編號排序，產生新檔，不覆寫原始檔。
- UI 的切分選項只在已有錄音加入佇列後出現；空佇列時不顯示可執行的切分動作。

### 3. 最後補驗證與失敗復原

除了原本的 mock pipeline，增加：

- 詞庫解析測試。
- Prompt echo 與 glossary echo 測試。
- 逐段 manifest 與合併測試。
- 失敗段落不得產生部分正式 TXT 的管線測試。
- 真實 Apple Silicon／Metal／Qwen 路徑測試。

## 三、實際改了什麼

### 長錄音與佇列

- `AudioSegmentPlanner`、`TranscriptionSourceSlice` 與 segment manifest 負責切分、排序及完整性 gate。
- 前端新增「切分再依序轉」操作；第二段會留在佇列，不會搶先執行。
- `TranscriptMerger` 依分段編號排序合併 TXT，輸出新檔，並拒絕空白或不合法內容。

### 輸出契約

- 在逐段輸出、合併後、OpenCC 後都重新驗證。
- 拒絕 BOM、NUL、空白輸出、Prompt 前置／尾端回吐及完整詞庫回吐。
- 只要最後沒有足夠可用文字，就維持 fail-closed，不寫出假成功檔案。

### helper 與模型生命週期

- 長駐 helper 使用 compact JSONL，避免 pretty JSON 被逐行解析時造成 `JSONDecodeError`。
- 同一批工作盡量重用 helper、engine 及 model cache。
- 如果模型只回傳送入的 Prompt／詞庫，helper 回報明確的 `prompt_echo_only`，而不是交給上層當成成功文字。

### 中文詞庫解析

詞庫原本主要支援逗號、頓號、分號及換行，這不足以處理使用者實際輸入的：

```text
味全 典華 學習長
```

現在連續的中文詞彙可以用空格分開；英文多字詞或中英混合詞則不任意拆開，例如 `One Company One Mission` 仍保留為一個詞。

## 四、為什麼過程中會看起來有這麼多 bug

這不是一個 bug 重複發生很多次，而是幾種不同層次的問題同時暴露出來。

### 1. 需求在實作中又擴大了

最初主要是 watchdog、磁碟檢查、歷史工作、模型載入及輸出驗證；後來又加入前端切兩段、第二段排隊、TXT 合併。這些功能都碰到同一條佇列與轉錄管線，沒有先重新整理完整的驗收矩陣，就容易出現「功能做了，但使用者找不到」或「分段工作能建立，但結果狀態不一致」的問題。

### 2. UI 顯示條件和使用者期待沒有一開始對齊

使用者期待的是「導入後，在開始轉文字旁就能切分」。實作上的按鈕確實依賴已加入佇列的檔案；在空佇列畫面中看不到是預期狀態，但畫面只留下提示文字時，很容易被理解成按鈕消失。

這是可發現性問題，不是核心切分功能不存在。後續驗收必須固定檢查至少四個狀態：空佇列、已加入一個檔案、切分後兩個工作、正在執行中。

### 3. 一開始只有「結構有效」的驗證，沒有完整處理「語意上是詞庫回吐」

程序正常結束、檔案非空，並不代表它是逐字稿。Qwen 在某些情況會把 system prompt 或詞庫原樣回吐；如果只檢查「有沒有文字」，就會把錯誤輸出當成成功。

最初的防護對「分開的多個詞」比較有效，卻漏掉了整句中文詞庫被 parser 當成一個詞的情況，也漏掉了模型在詞與詞之間加上句號的情況。這說明輸出契約必須建立在 parser 的真實輸出與模型實際行為上，不能只寫一個理想格式的判斷。

### 4. 測試資料沒有一開始就包含真實模型的失敗樣式

mock ASR 能驗證流程、取消、失敗復原及合併順序，但不能代表 Qwen 在真實 Metal 路徑上的回吐行為。真正的 `味全 典華 學習長` 與 `味全。典華。學習長。` 是在真實測試時才看見，之後才補進 parser、chunking、validator 及 self-test。

### 5. 歷史狀態和輸出正確性是兩個不同問題

畫面裡的綠色「完成」是舊版本已寫入的歷史狀態；它不會因新版本加入 validator 就自動回溯檢查舊 TXT。紅色「失敗」才是新版本的 fail-closed 行為。

因此同一個檔案會同時看到綠色完成與紅色失敗，看起來像新版本忽好忽壞，其實是兩批不同時間、不同防護邏輯的結果。

### 6. 測試音檔本身還有獨立的品質問題

同一個音檔拿掉詞庫後仍沒有產生可用文字；已確認它的平均音量約為 `-39.1 dB`、最大音量約為 `-20.3 dB`。所以不能把所有失敗都歸因於詞庫 bug：詞庫回吐是已修正的輸出契約問題，但這個檔案本身可能還有音量、錄音品質或模型辨識問題。

## 五、逐次 Debug 過程

### 第一次：發現 TXT 只有詞庫

實際產物是：

```text
味全 典華 學習長。
```

先檢查輸出檔，而不是先猜模型。接著查看 job snapshot，發現詞庫被儲存成：

```json
{"terms":["味全 典華 學習長"]}
```

根因是 `TermParser` 沒有把空格分隔的中文詞拆開；後續的 echo 防護也因此沒有拿到三個獨立詞條。

修正：

- parser 對中文詞彙支援空格拆分。
- `remove_prompt_echo()` 對舊 snapshot 再做一次相同展開。
- validator 同樣展開詞條，避免只修 parser、漏掉歷史工作。
- 加入中文空格詞庫測試。

### 第二次：模型在詞條間加入句號

修正後又出現：

```text
味全。典華。學習長。
```

這代表第一個修正只處理了「詞條是否拆開」，沒有處理模型自行插入標點。原本的 separator 只涵蓋逗號、頓號、分號等，沒有涵蓋句號、驚嘆號及問號。

修正：

- echo remover 支援句號等句末標點作為詞條間隔。
- validator 改成依序消費完整詞庫，允許中間出現標點與空白。
- 補上「標點分隔的完整詞庫回吐」測試。

### 第三次：不再產生假 TXT，但工作變成失敗

加入清除 echo 後，如果模型整段輸出都只是詞庫，清除完會變成空字串。這時不能讓上層把空字串當成成功，也不能默默產生一個看似完成的檔案。

修正後 helper 回報：

```text
prompt_echo_only：模型只回吐了送入的 Prompt／詞庫，沒有產生可用逐字稿。
```

這就是截圖中新的紅色失敗。它看起來比綠色完成更不好看，但實際上是正確的失敗：錯誤已被攔在輸出契約，而不是被寫進正式 TXT。

### 第四次：做無詞庫對照測試

為了確認是不是詞庫造成全部問題，拿掉詞庫重新跑同一個音檔。結果仍然沒有可用文字，且音檔音量偏低。

結論是：

- 詞庫回吐問題：已確認、已修正。
- 這個音檔本身沒有產生可用 ASR 文字：已確認仍存在，但不能再歸咎於詞庫 parser。
- 後續應另做音訊增益／品質提示與模型辨識測試，不應為了讓畫面變綠而放寬輸出驗證。

### 第五次：解釋為什麼畫面同時有綠色和紅色

檢查 recent jobs 及 recovery 資料後，確認綠色項目是舊測試留下的歷史完成紀錄，紅色項目是新防護後的失敗紀錄。App 目前沒有對舊完成項目做內容重新驗證，因此歷史顏色不會自動改變。

這也提醒我們：完成狀態應該區分「當時流程完成」與「目前內容通過最新契約」，否則在 validator 演進後，舊資料會造成判讀混亂。

## 七、這次最重要的學習

### 1. 「程序成功」和「內容成功」必須分開

ASR helper exit code 是 0、TXT 非空，只能證明程序有輸出；不能證明輸出是逐字稿。內容契約必須是正式管線的一部分。

### 2. Prompt 的輸入格式要和輸出防護共用同一套 parser

如果輸入端把三個中文詞當成一個詞，輸出端再怎麼比對三個詞都會失效。Parser、Prompt builder、echo remover、validator 不能各自維持一套不同規則。

### 3. Mock 測試不能取代真實模型 smoke test

流程測試仍然必要，但凡是 Prompt、模型輸出、詞庫或 chunking 的改動，都要有最小真實 Metal 測試，並保留一個「無詞庫對照組」。

### 4. 歷史資料要有版本與重新驗證策略

新規則不會自動修正舊結果。至少要能標示「舊版本完成、尚未以目前契約重新驗證」，避免使用者把歷史狀態當成目前仍然可信。

### 5. UI 驗收要用狀態矩陣，不要只看空畫面

對條件式顯示的功能，不能只啟動 App 看一眼。要逐一驗證空佇列、已導入、切分後、執行中、完成、失敗及復原狀態。

### 6. 保留證據再清理測試產物

這次保留了錯誤 TXT、job snapshot 與 recovery 資料，才能追出 parser 和模型輸出的差異。除非明確知道哪些是測試產物，否則不應為了讓畫面乾淨就先刪除。

## 八、目前仍未完全解決的事

- 這個低音量音檔如何穩定辨識，仍需獨立處理；目前正確策略是 fail-closed。
- 舊的綠色完成歷史項目不會自動重新驗證。
- `Fetching 11 files` 的 cache reuse 已實作，但實際耗時與記憶體改善仍需用真實長音檔做前後測量。
- PD-015 自動檢查更新尚未實作。
- 完整 Runtime installer、簽署、公證及 Stable DMG 仍不在目前 Phase 0 範圍。

## 九、下一次應採用的開發順序

1. 先寫需求與驗收矩陣，固定 UI 狀態、輸入格式、成功條件及失敗條件。
2. 先建立 glossary echo、Prompt echo、空白輸出及低音量音檔的 golden cases。
3. 再改 parser、helper、validator 與 UI，避免只在最後才發現幾個元件的規則不一致。
4. 每完成一個模型輸出相關修正，立即跑 mock + real Metal + 無詞庫對照。
5. 最後才清理 recovery／history 測試資料，並明確區分測試產物與使用者原始檔。

這次的核心教訓不是「多加幾個 if 就好」，而是要把 ASR 的內容正確性當成一級資料契約，並讓 UI、佇列、helper、歷史紀錄和測試都遵守同一個契約。
